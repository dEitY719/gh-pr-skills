gh-pr skills

GitHub 워크플로의 브랜치 절반을 담당하는 스킬 8개 — 커밋할 것이 생긴 순간부터 PR 이 머지되고 그 브랜치가 사라질 때까지. 스킬마다 설명서 1건과 사용 예시 1건이 있습니다.

commit─▶ create─▶ review─▶ reply─▶ approve─▶ merge
여기에 read-only 스킬은 없습니다 — 8개 전부 live 저장소에 씁니다. 그래서 각 스킬의 안전 계약은 권고가 아니라 하드 룰입니다. 사용 예시 문서는 그 이유로 미실행 예시이며, 명령과 게이트는 각 SKILL.md 인용입니다.

1스킬 8개

commit

/gh-pr:commit [issue] [remote]

저장소 고유의 스타일로 커밋 1개를 만들고 이슈를 연결한다. push 도 PR 생성도 하지 않는다 — 사람이 diff 를 먼저 검토하도록 일부러 나눈 경계다.

설명서 사용 예시

create

/gh-pr:create [issue] [remote]

브랜치가 base 에서 분기한 이후의 모든 커밋을 묶어 Pull Request 를 연다. HEAD 하나가 아니다. 리뷰도 머지도 하지 않는다.

설명서 사용 예시

review

/gh-pr:review <PR#> --ai <cli>

외부 AI CLI 하나에 2차 의견을 위임하고 집계 코멘트 1개를 남긴다. 판정을 제출하지 않고 코멘트별 답글도 달지 않는다.

설명서 사용 예시

reply

/gh-pr:reply <PR#> [remote]

봇을 포함한 모든 리뷰 코멘트에 개별 답글을 달고, 타당한 지적은 실제로 고친다. 요약 코멘트 1개는 답글 패스가 아니다.

설명서 사용 예시

approve

/gh-pr:approve <PR#> [remote]

판정을 제출하는 유일한 스킬. blocker 는 request changes 가 되고 나머지는 후속 이슈가 된다. 자기가 작성한 PR 은 승인할 수 없다.

설명서 사용 예시

merge

/gh-pr:merge <PR#> [strategy]

기본 rebase, squash/merge 선택 가능. 미승인 · CI 실패 · draft · conflict 는 강행하지 않고 거부한다. 항상 --delete-branch.

설명서 사용 예시

merge-emergency

/gh-pr:merge-emergency <PR#> "<reason>"

그 거부의 유일한 우회로이고, 사유 코멘트와 후속 인시던트 이슈로 대가를 치른다. 우회 대상은 승인 요건뿐 — CI 는 여전히 게이트한다.

설명서 사용 예시

merge-train

/gh-pr:merge-train [repo] [remote]

자기가 연 열린 PR 을 한 번에 하나씩 훑으며 각각 resolve 스킬로 보낸 뒤 merge 에 넘긴다. merge 단독이라면 거부했을 것을 머지하지 않는다.

설명서 사용 예시

2두 개의 분리선

권한 — review / approve

review 는 바깥의 의견을 모으기만 하고 코멘트밖에 남기지 못한다. approve 는 판정이 제출되는 유일한 자리다. 그 사이에 reply 가 있고, 수정이 실제로 안착하는 곳이 거기다.

머지 — merge / merge-emergency

같은 분리선을 머지에 적용한 것이다. 앞은 거부하고 뒤는 우회한다. 그리고 그 우회의 대가를 서면으로 치른다 — 사유 코멘트와 인시던트 이슈.
